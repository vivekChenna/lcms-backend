# Task 6 — Case schemas

**Date:** 2026-10-04

**What:** Created `src/modules/cases/cases.schemas.ts` with Zod schemas for case operations: const arrays `CASE_STATUSES`, `CASE_PRIORITIES`, `SLA_STATES`; request body schemas `createCaseBodySchema` (with `declarationConfirmed: true` enforcement and `priority` default to P3), `updateCaseBodySchema`, `updatePriorityBodySchema`, `assignCaseBodySchema`, `rejectAssignmentBodySchema`, `escalateCaseBodySchema` (with conditional reason validation), `closeCaseBodySchema` (with `confirm: true` enforcement); param schema `caseIdParamsSchema`; query schema `caseListQuerySchema` (extends pagination with optional filters); and response schemas `caseResponseSchema` and `caseListResponseSchema`. All seven test cases in `test/unit/modules/cases/cases.schemas.test.ts` validate request/response structure, validation rules (min lengths, UUID formats, literal enforcement, conditionals), and defaults.

**Why:** Routes in Tasks 7–14 need standardized, validated request/response contracts to accept user input, enforce business rules (e.g., case submission requires declaration confirmation; escalation requires a reason), and serialize case entities for API consumers. Zod schemas provide compile-time TypeScript type inference and runtime validation in a single source of truth, eliminating boilerplate and reducing the surface for injection or malformed-data bugs. Embedding validation logic in schemas (e.g., `z.literal(true)` for required confirmation, `.refine()` for conditional reason) keeps rules visible alongside the contracts that enforce them, making maintenance straightforward for future tasks that consume these schemas.
