# Task 9 — Case submission

**Date:** 2026-10-04

**What:** Added `POST /cases` end-to-end: `src/modules/cases/cases.service.ts` exports `submitCase(dataSource, actor, input)`, which validates `categoryId`/`caseTypeId`/`departmentId` are known and active, enforces that a `requester` may only submit into the `Internal` category (VC-03) while other roles may use any category, derives `entityId`/`businessUnitId` from the requester's own profile when the actor is a requester (PR-02 — pre-filled, non-editable) or from the body otherwise, validates `caseTypeId` belongs to `categoryId` (VC-04) and `businessUnitId` belongs to `entityId` (VC-05), computes SLA due dates via `computeDueDates` (Task 4), generates the reference number via `generateReferenceNumber` (Task 3) off the real `case_reference_seq` Postgres sequence (Task 1 migration) for atomicity under concurrent submissions, persists the `Case` row as `Submitted`, logs a `case.submitted` audit event, then runs `evaluateAutoRouting` (Task 5) and — if a rule matches — calls `assignCase` (Task 7) with `auditAction: 'case.auto_assigned'` so the response reflects the auto-assigned state. `cases.routes.ts` wires `POST /cases` (`requireRole(['requester', 'legal_rep', 'admin'])`, body validated by `createCaseBodySchema`) and returns `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)` — same Task 7/8 convention, since `caseResponseSchema` declares its six timestamp fields as `z.string()` while `toCaseWithSla` returns native `Date`s, and fastify-type-provider-zod does not coerce between them. Added `test/integration/modules/cases/submit.test.ts` (7 cases): requester submitting Internal (201, reference number format, SLA dates, audit log), requester rejected for non-Internal (400, VC-03), legal_rep submitting any category (201), caseTypeId/categoryId mismatch rejected (400, VC-04), businessUnitId/entityId mismatch rejected (400, VC-05), auto-assignment via a matching routing rule (201, status `Assigned`, `case.auto_assigned` audit row), and 5 concurrent submissions producing 5 distinct reference numbers.

**Why:** `createCaseBodySchema` (Task 6) originally declared `entityId` as a required UUID in the request body, which is incompatible with PR-02: a requester's submission never includes `entityId` at all (it's pre-filled from their profile), so the brief's own first test — a requester submitting without `entityId` in the payload — would fail Zod validation (400) before ever reaching `submitCase`, never getting the expected 201. Made `entityId` optional in `createCaseBodySchema`, mirroring the existing `businessUnitId` field, and made `CreateCaseInput.entityId` optional in `cases.service.ts` to match; `submitCase` now throws a `ValidationError` if `entityId` is missing for any role other than `requester` (legal_rep/admin must supply it directly). No existing schema unit test exercised the omitted-`entityId` case, so this is additive, not a behavior change for any role that already supplies it.

The brief's literal test for the first case also renamed a freshly-seeded category to `'Internal'` via `UPDATE case_categories SET name = 'Internal'`. That collides, on every run (not just a polluted container), with the row literally named `'Internal'` that migration `1700000003000-create-simple-master-data.ts` permanently seeds (alongside `Najiz`, `Baladi Violation`, `HR Termination`) — confirmed by reproducing the failure against a freshly recreated test container. The test instead looks up that pre-seeded `'Internal'` row's own id and inserts a case type scoped to it, rather than renaming a second row into a name collision.

Full-suite note: running the entire `test/integration` directory surfaces one pre-existing, order-dependent failure unrelated to this task — `case-categories.test.ts`'s "lists the four seeded case categories (DM-01)" asserts an exact count of 4 seeded categories, which breaks once any earlier-running suite (several `cases/*.test.ts` files predating this task, e.g. `case-entity.test.ts`, `assign.test.ts`, `accept-reject.test.ts`) adds rows to the shared `case_categories` table via `seedCaseMasterData`. Verified via `git stash` that this same failure occurs identically with and without this task's changes — it is not a regression introduced here, and `case-categories.test.ts` is not one of this task's files.
