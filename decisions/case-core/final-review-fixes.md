# Final review fix wave — VC-03/04 edit bypass, legal_manager accept/reject, closure validation, test isolation

**Date:** 2026-10-04

**What:** Fixed all four Important findings from the final whole-branch review of case-core, in one coordinated pass (no second review round follows, so each fix was verified individually before moving on, plus two full-suite runs on fresh containers at the end).

1. **Test suite failed on a clean database (three causes, all in test code only):**
   - `test/integration/modules/master-data/case-categories.test.ts`: the `lists the four seeded case categories (DM-01)` test asserted the category list was *exactly* the 4 migration-seeded names. Case-core's `seedCaseMasterData` (`test/integration/helpers/seed-case.ts`) inserts its own `Category-xxxx` rows with no cleanup, and when `cases/*` test files run (alphabetically) before `master-data/*` ones in the same vitest process, those leftover rows make the exact-count assertion fail. Changed the assertion to `expect(names).toEqual(expect.arrayContaining([...]))`, the same subset-check pattern Task 1 already applied to `org-structure.test.ts` for an identical problem.
   - `seedCaseMasterData` derived `entities.code` from only 3 hex characters of a random UUID (`suffix.slice(0, 3).toUpperCase()`, 4096 possible values) — a real collision was hit in the reviewer's testing, which trips the `entities.code` unique constraint. Widened it to the full 8-hex-character suffix already computed at the top of the function (`E${suffix.toUpperCase()}`, 16^8 possible values). The `entities.code` column (`src/db/migrations/1700000004000-create-entities-and-business-units.ts`) is an unbounded `varchar`, so the longer code needed no migration change. This did lengthen generated reference numbers beyond what `submit.test.ts`'s `/^E\w{3}-\w{3}-\d{6}$/` regex allowed for the entity-code segment; relaxed that one assertion to `/^E\w{3,}-\w{3}-\d{6}$/` (still pins the fixed caseType-code/sequence segments, just not the now-variable-length entity code).
   - `test/integration/modules/cases/case-entity.test.ts` (added by Task 1's fix round) ran `DELETE FROM case_categories` and `DELETE FROM entities` in its own test body, wiping the migration-seeded rows (including the real `'Internal'` category) that `submit.test.ts` depends on when both files share one test-process container without a reset between them. Removed just those two `DELETE` lines — the test only needs `cases`/`users`/`user_roles`/`business_units`/`case_types`/`departments` empty before inserting its own randomly-named fixture rows via `seedCaseMasterData`; it never required `case_categories`/`entities` to be empty.

2. **`updateCase` (`src/modules/cases/cases.service.ts`) bypassed VC-03 and VC-04:**
   - VC-03: a requester could submit an Internal-category case, then `PATCH` it to a non-Internal `categoryId` — the Internal-only restriction was only checked in `submitCase`. Now, whenever `input.categoryId` is present in a `PATCH /cases/:id` body and `actor.role === 'requester'`, the fetched target category's `name` is checked against `'Internal'` (same rule `submitCase` applies at creation), throwing `ValidationError` otherwise.
   - VC-04: the `caseType.categoryId !== effectiveCategoryId` check was gated behind `input.caseTypeId && input.caseTypeId !== caseRow.caseTypeId` — so changing only `categoryId` (with `caseTypeId` omitted from the body) skipped it entirely, letting a case end up with a `caseTypeId` that didn't belong to its new category. The check now runs whenever *either* `input.categoryId` or `input.caseTypeId` is present, always against the *effective* pair (`input.caseTypeId ?? caseRow.caseTypeId` vs. `input.categoryId ?? caseRow.categoryId`).
   - Added two tests to `test/integration/modules/cases/update-case.test.ts`: a requester PATCHing their Internal case to a non-Internal category (400), and an admin PATCHing only `categoryId` on a case whose existing `caseTypeId` doesn't belong to the new category (400) — the latter uses an admin actor (not the requester) specifically to isolate VC-04 from the separate VC-03 check added above.

3. **A case assigned to a `legal_manager` could never be accepted or rejected:** `assertValidLegalRep` (`src/modules/master-data/routing-rules.service.ts`, VC-07) allows manual assignment and auto-routing to target a `legal_manager`, but `PATCH /cases/:id/accept` and `PATCH /cases/:id/reject` (`src/modules/cases/cases.routes.ts`) were gated with `requireRole(['legal_rep'])` only, so a legal_manager who was the actual assignee could never call either route — the case would be stuck in `Assigned` forever. Widened both routes' `requireRole` to `['legal_rep', 'legal_manager']`. No service-layer change was needed: `acceptAssignment`/`rejectAssignment` already check `caseRow.assignedLegalRepId === actorId`, which correctly restricts the action to whoever is actually assigned regardless of role. Added a test to `test/integration/modules/cases/accept-reject.test.ts` covering a `legal_manager` accepting a case assigned to them.

4. **An invalid `closureOutcomeId` caused a 500 instead of a 400:** `closeCase` (`src/modules/cases/cases.workflow.service.ts`) saved `input.closureOutcomeId` without validating it referenced a real, active `ClosureOutcome` row. An unknown id tripped the database's foreign-key constraint (Postgres `23503`), which `src/plugins/error-handler.ts` doesn't map (it only maps `23505` unique violations), so the client got a raw 500. Added a `ClosureOutcome` lookup before the save, throwing `ValidationError('Unknown or inactive closureOutcomeId')` when the row is missing or `isActive` is false — the same pattern `submitCase` already uses for its other master-data foreign keys. Added a test to `test/integration/modules/cases/close.test.ts` for an unknown `closureOutcomeId` (expects 400).

**Why one combined decisions entry instead of four:** these were reviewed and fixed together as a single wave (the last one before ship), not as four independently-scoped tasks — splitting the log into four files would misrepresent how the work actually happened and make it harder to see that the whole-suite verification at the end covers all four fixes at once, not each in isolation.

**Final verification:** after all four fixes, ran the entire backend suite — `npx vitest run test/unit test/integration` — twice in a row, each time against a genuinely fresh container (`docker compose -f docker-compose.test.yml down && docker compose -f docker-compose.test.yml up -d`, port 5433), specifically because an earlier claim in this project that "a single fresh run is reliably green" turned out to be false (that's Finding 1 above). Also ran `npx tsc --noEmit`. See the fix-report at `.superpowers/sdd/2026-10-01-case-core/final-review-fix-report.md` for exact commands and output.
