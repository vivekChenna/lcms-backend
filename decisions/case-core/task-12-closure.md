# Task 12 — Closure

**Date:** 2026-10-04

**What:** Added `PATCH /cases/:id/close` end-to-end. `src/modules/cases/cases.workflow.service.ts` exports `closeCase(dataSource, actor, caseId, input: {closureSummary, closureOutcomeId})`, which loads the case (`loadCaseOrThrow`, throwing `NotFoundError` for a missing id), validates the status transition to `Closed` via `assertTransition` (only `In Progress -> Closed` is a legal edge per the state machine; `Assigned`/`Submitted`/`Waiting on Input` are not), then authorizes the actor — the assigned legal rep (`caseRow.assignedLegalRepId === actor.id`) or a `legal_manager`/`admin`, anyone else gets `ForbiddenError` — then sets `status = 'Closed'`, `closureSummary`, `closureOutcomeId`, `closedById`, and `closedAt`, saves, and writes an audit event (`case.closed`) with before/after snapshots. `cases.routes.ts` wires it as `PATCH /cases/:id/close`, gated by `app.authenticate` + `requireRole(['legal_rep', 'legal_manager', 'admin'])`, validated by `caseIdParamsSchema` (params) and the existing `closeCaseBodySchema` (body — `{ confirm: z.literal(true), closureSummary: z.string().min(1), closureOutcomeId: z.string().uuid() }`, already present in `cases.schemas.ts` since an earlier task), response `caseResponseSchema`. Added `test/integration/modules/cases/close.test.ts` (4 cases): the assigned legal_rep closes an In Progress case, closing a still-Submitted case is rejected with 409, a legal_rep NOT assigned to the case is rejected with 403, and omitting `confirm: true` is rejected with 400 (by the body schema, before the handler runs).

VC-12's "no open information requests" guard is deferred to sub-project 2 (that table doesn't exist yet) — see spec §3/§8. Same deferral as noted in the task brief.

**Why — `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)`:** Same latent-contract mismatch documented in Tasks 7-11's decision logs: `toCaseWithSla` returns native `Date` instances for six timestamp fields, while `caseResponseSchema` declares them as `z.string()`. Returning the un-serialized row through fastify-type-provider-zod would 500 with `FST_ERR_RESPONSE_SERIALIZATION`. The route calls the already-exported `serializeCase` helper from `cases.routes.ts` (the same helper every prior case-mutation route in this file uses) instead of the brief's literal `return toCaseWithSla(caseRow);`, and instead of reintroducing the bug or duplicating the Date-to-ISO-string conversion.

**Why the order was swapped — transition check before authorization check:** The brief's literal `closeCase` body (Step 3) checked ownership/role first, then called `assertTransition`. Running the test suite against that literal order failed test 2 ("rejects closing a case that is still Submitted (VC-14)"): that test seeds a case with `status: 'Submitted'` and no `assignedLegalRepId` (correct, since a Submitted case has no assignment yet), then has a `legal_rep` who is *not* the (non-existent) assigned rep attempt to close it. With ownership checked first, `caseRow.assignedLegalRepId === actor.id` is `null === repId`, i.e. false, and the actor is not a manager/admin either, so the handler threw `ForbiddenError` (403) before ever reaching `assertTransition` — but the test (and VC-14's intent, "wrong status blocks closure") expects 409. Swapping the two checks so `assertTransition` runs first fixes this: an invalid-status case now reliably reports 409 regardless of who's attempting it, and `ForbiddenError` is only reached once the transition itself is legal. Traced by hand against all 4 tests to confirm the swap doesn't change any other outcome: the happy path (owning rep, valid transition) and the not-assigned-rep test (another legal_rep, valid `In Progress -> Closed` transition, wrong actor) both still land on their original expected status codes (200 and 403 respectively).

**Note — no query-builder alias concern here:** `closeCase` only uses `dataSource.getRepository(Case).findOne()` / `.save()` (via the existing `loadCaseOrThrow` helper), not a `createQueryBuilder` with a string alias, so the Task 10 `'case'`-is-a-reserved-keyword issue doesn't apply to this task's code.

**Test-container note:** a first full run of `test/integration/modules/cases/` showed one unrelated failure in `submit.test.ts` (a `category.id` lookup returning `undefined`), consistent with the known pre-existing cross-run test-pollution issue in shared master-data tables. Recreating the test container (`docker compose -f docker-compose.test.yml down && up -d`) and re-running both `submit.test.ts` alone and `close.test.ts` alone confirmed both pass cleanly on a fresh container — the failure was pre-existing pollution from accumulated prior runs, not a regression from this task's changes.
