# Task 14 — Priority changes

**Date:** 2026-10-04

**What:** Added `PATCH /cases/:id/priority` end-to-end — the final route of the case-core module. `src/modules/cases/cases.service.ts` exports `updatePriority(dataSource, actorId, caseId, priority): Promise<Case>`, which loads the case (`NotFoundError` if missing), rejects with `ConflictError` if `caseRow.status === 'Closed'` (PR-19: priority may be changed in any open status, not just before routing), otherwise assigns the new `priority`, saves, and writes a `case.priority_changed` audit event with before/after `{ id, priority }` snapshots (after also includes `referenceNumber`, matching the convention of every other mutation in this file). `cases.routes.ts` wires it as `PATCH /cases/:id/priority`, gated by `app.authenticate` + `requireRole(['legal_manager', 'admin'])` — unlike `updateCase`/`closeCase`, there is no actor-ownership check inside the service; the role gate is the only authorization check, and it runs entirely in the Fastify `preHandler` before the service is ever called. Validated by `caseIdParamsSchema` (params) and the already-present `updatePriorityBodySchema` (body, added to `cases.schemas.ts` in an earlier task alongside the other case schemas, unused until now), response `caseResponseSchema`. Added `test/integration/modules/cases/update-priority.test.ts` (3 cases): a `legal_manager` changes priority on an `In Progress` case (200, priority updated, one `case.priority_changed` audit row — PR-19), a `legal_rep` is rejected (403, caught by the role gate before the service runs), and changing priority on a `Closed` case is rejected (409).

**Why `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)`:** Same latent-contract mismatch documented in every case-mutation route since Task 7: `toCaseWithSla` returns native `Date` instances for six timestamp fields, while `caseResponseSchema` declares them as `z.string()`. Returning the un-serialized row through fastify-type-provider-zod would 500 with `FST_ERR_RESPONSE_SERIALIZATION`. The route calls the already-exported `serializeCase` helper from `cases.routes.ts` instead of a bare `return toCaseWithSla(caseRow);`.

**Why the brief's literal check order needed no reordering, unlike Task 12:** Task 12's `closeCase` had to swap its check order because a test combined "wrong actor" with "invalid status" on the same case, and an in-service ownership check run first masked the intended 409 behind a 403. This task has only one check inside the service (`status === 'Closed'`) — the role/authorization check lives entirely in `requireRole`, a Fastify `preHandler` that runs and can short-circuit the request before the handler (and therefore `updatePriority`) is ever invoked. There is structurally no way for the service's status check to run before or interact with the role gate's 403, so no test combining "wrong role" with "Closed case" on the same case could produce ambiguous masking either way: the 403 test (`legal_rep`) uses an `In Progress` case, and the 409 test (`legal_manager`, correct role) uses a `Closed` case. Traced by hand against all 3 tests before concluding no reordering was needed; confirmed by the actual green run below.

**Final verification (last task of case-core):** ran the full module suite together — `npx vitest run test/unit/modules/cases test/integration/modules/cases` — against a freshly recreated test container (`docker compose -f docker-compose.test.yml down && up -d`, port 5433) to rule out cross-task master-data pollution in the shared container.
