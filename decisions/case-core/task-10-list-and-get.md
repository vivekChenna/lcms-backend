# Task 10 — Listing and detail (visibility matrix)

**Date:** 2026-10-04

**What:** Added `GET /cases` and `GET /cases/:id` end-to-end. `src/modules/cases/cases.service.ts` exports `listCases(dataSource, actor, query)`, which builds a TypeORM query over `Case`, scopes the result to the actor's own `departmentId` when `actor.role === 'requester'` (AC-04) and leaves it unscoped for every other role (`admin`, `legal_manager`, `legal_rep`, `viewer` all see every case read-only per AC-05/AC-07), applies the optional `status`/`priority`/`categoryId`/`caseTypeId`/`entityId`/`businessUnitId`/`departmentId`/`assignedLegalRepId`/`search` filters, derives the `slaState` filter (`on_track`/`at_risk`/`breached`/`met`) from the same percentage-of-window rule as `deriveSlaState` (Task 4), paginates via `paginationToSkipTake` (shared pagination helper), and maps each row through `toCaseWithSla` (Task 4). `getCaseById(dataSource, actor, caseId)` loads a single case and throws `NotFoundError` both when the row doesn't exist and when a `requester` looks up a case outside their department — a deliberate 404-not-403 to avoid confirming a case id's existence to someone who can't see it. `cases.routes.ts` wires both as `GET /cases` (query validated by `caseListQuerySchema`, response by `caseListResponseSchema`) and `GET /cases/:id` (params validated by `caseIdParamsSchema`, response by `caseResponseSchema`), both gated only by `app.authenticate` — no `requireRole`, since every role in the system has some form of read access to cases. Added `test/integration/modules/cases/list-and-get.test.ts` (6 cases): admin sees all cases across departments, legal_rep sees all cases including ones not assigned to them (AC-05), requester sees only their own department's cases (AC-04) and the returned row reflects that department, viewer sees all cases (AC-07), a requester fetching a case outside their department gets 404, and `slaState=breached` filtering returns only the matching case.

**Why — serializeCase applied at the route layer, not inside `cases.service.ts`:** Task 7 established that `toCaseWithSla` (Task 4, approved, pinned by its own unit test) returns native `Date` instances for the six timestamp fields, while `caseResponseSchema`/`caseListResponseSchema` (Task 6, approved) declare those fields as `z.string()` for the OpenAPI/JSON contract — fastify-type-provider-zod does not coerce between the two, so returning a bare `toCaseWithSla(caseRow)` through either route would 500 with `FST_ERR_RESPONSE_SERIALIZATION`. The existing fix, `serializeCase` (exported from `cases.routes.ts`, reused as-is by Tasks 7, 8, 9), lives in the routes file, not the service file. `listCases`/`getCaseById` are written exactly as specified, still calling `toCaseWithSla` internally and returning `Date`-bearing rows; `cases.routes.ts` applies `serializeCase` on the way out instead — `result.items.map(serializeCase)` for the list route, `serializeCase(caseRow)` for the detail route — keeping `cases.service.ts` free of a reverse dependency on `cases.routes.ts` and matching the pattern every prior task already uses.

**Why — query-builder alias renamed from `case` to `c`:** Implementing `listCases` with the alias exactly as given (`createQueryBuilder('case')`) reproduced a real 500 the first time any test exercised a camelCase, quotes-required column through it: `qb.andWhere('case."departmentId" = :actorDepartmentId', ...)` — the requester-department-scoping filter, exercised by the "requester sees only their own department's cases" test — sent Postgres `WHERE case."departmentId" = $1` with the alias `case` itself left unquoted, and Postgres rejects that outright because `CASE` (the `CASE WHEN` expression) is a fully reserved keyword that cannot appear as any kind of identifier, qualified or not, without quoting. The reason `case.status = :status` and `case.priority = :priority` elsewhere in the same literal code did *not* fail is incidental, not safe: TypeORM's query-builder only rewrites a bare `alias.property` reference into a properly quoted `"alias"."property"` when the property name itself is left unquoted and matches a known entity property; once the property is written pre-quoted (`case."departmentId"`), that rewrite doesn't fire and the literal string — alias included — goes straight to Postgres. Renaming the alias to `c` throughout `listCases` (every `andWhere`/`orderBy` call, including the ones that happened to work) removes the reserved-word collision at its root instead of leaving a trap for the next quoted-property filter (`categoryId`, `caseTypeId`, `entityId`, `businessUnitId`, `assignedLegalRepId` were all written with the same unsafe pattern and are exercised by no test in this task, so a partial fix would have shipped a latent 500 in four more query parameters). Confirmed via a reproduction run: with the alias left as `'case'`, the department-scoping test failed with `QueryFailedError: syntax error at or near "."`; after the rename to `'c'`, the full 6-test file passes.

Full-suite note: `test/integration/modules/cases/submit.test.ts` failed once during this task's work (`internalCategory` lookup returning `undefined`) on a container that had already been used for several earlier debugging runs in the same session; re-running it alone, and together with `list-and-get.test.ts`, against a freshly recreated `docker-compose.test.yml` container passed cleanly (7/7 and 13/13 respectively) — consistent with the known pre-existing cross-file master-data pollution noted in Task 9's own log, not a regression from this task's changes.
