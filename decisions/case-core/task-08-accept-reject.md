# Task 8 — Accept and reject

**Date:** 2026-10-04

**What:** Added `PATCH /cases/:id/accept` and `PATCH /cases/:id/reject` to `src/modules/cases/cases.routes.ts`, both gated to `legal_rep` via `requireRole(['legal_rep'])`. They call the already-existing `acceptAssignment`/`rejectAssignment` from `cases.workflow.service.ts` (Task 7), with `/reject` validated against `rejectAssignmentBodySchema` (Task 6, `reason: z.string().min(3)`). Added `test/integration/modules/cases/accept-reject.test.ts` (5 cases): the assigned `legal_rep` accepting (200, status flips to `In Progress`, `assignmentAcceptedAt` stamped), a non-assigned `legal_rep` attempting accept (403), the assigned `legal_rep` rejecting with a reason (200, status returns to `Submitted`, `assignedLegalRepId` cleared to `null`), a reject reason under 3 characters failing schema validation (400, VC-08), and accepting a case that isn't currently `Assigned` (409, via `assertTransition`).

**Why:** Both service functions and the reassignment-reset behavior in `assignCase` were already built and tested in Task 7 specifically so this task would be a thin route-wiring exercise — `acceptAssignment`/`rejectAssignment` already enforce the "only the assigned rep" ownership check (403) and reuse `assertTransition` (Task 2) for the state-machine guard (409), so the route handlers add no new business logic, only auth/schema wiring, matching the pattern established by the `/assign` route.

Per the ruling from Task 7, the route handlers return `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)`. `toCaseWithSla` returns native `Date` objects for `assignmentAcceptedAt`/`ackDueAt`/`resolutionDueAt`/`closedAt`/`createdAt`/`updatedAt`, while `caseResponseSchema` declares those fields as `z.string()`; fastify-type-provider-zod validates-then-serializes against that schema without implicit `Date`-to-string coercion, so returning the bare `Case` object would 500 with `FST_ERR_RESPONSE_SERIALIZATION` the moment a real request hit either route. `serializeCase`, exported from `cases.routes.ts` in Task 7 for exactly this reuse, converts those six fields to ISO strings (handling the three nullable ones correctly) before the response leaves the handler, so both new routes reuse the one conversion helper instead of re-deriving it.
