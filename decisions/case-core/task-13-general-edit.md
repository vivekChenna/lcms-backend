# Task 13 — General edit

**Date:** 2026-10-04

**What:** Added `PATCH /cases/:id` end-to-end. `src/modules/cases/cases.service.ts` exports `UpdateCaseInput` (`{ title?, description?, categoryId?, caseTypeId?, departmentId? }`) and `updateCase(dataSource, actor, caseId, input): Promise<Case>`, which loads the case (`NotFoundError` if missing), checks ownership — the submitter (`caseRow.requesterId === actor.id`) or an `admin`, anyone else gets `ForbiddenError` — then checks `caseRow.status === 'Submitted'` (`ConflictError` otherwise, since a case is only freely editable before it's routed), then re-validates `categoryId`/`caseTypeId`/`departmentId` if supplied: an unknown or inactive `categoryId`/`caseTypeId`/`departmentId` is rejected with `ValidationError`, and a supplied `caseTypeId` must belong to the effective `categoryId` (VC-04 cross-field rule, same as at submission in Task 9) or it's rejected. On success it applies only the fields present in `input`, saves, and writes a `case.updated` audit event with before/after snapshots of the editable fields plus `referenceNumber`. `cases.routes.ts` wires it as `PATCH /cases/:id`, gated by `app.authenticate` + `requireRole(['requester', 'legal_rep', 'admin'])`, validated by `caseIdParamsSchema` (params) and `updateCaseBodySchema` (body, already present in `cases.schemas.ts`), response `caseResponseSchema`. Added `test/integration/modules/cases/update-case.test.ts` (4 cases): the submitter edits their own Submitted case (200, title updated, one `case.updated` audit row), editing an Assigned case is rejected (409), editing by someone other than the submitter/admin is rejected (403), and an admin can edit any Submitted case (200).

**Why `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)`:** Same latent-contract mismatch documented in every case-mutation route since Task 7: `toCaseWithSla` returns native `Date` instances for six timestamp fields, while `caseResponseSchema` declares them as `z.string()`. Returning the un-serialized row through fastify-type-provider-zod would 500 with `FST_ERR_RESPONSE_SERIALIZATION`. The route calls the already-exported `serializeCase` helper from `cases.routes.ts` instead of the brief's literal `return toCaseWithSla(caseRow);`.

**Why the brief's literal check order (ownership before status) needed no swap here, unlike Task 12:** Task 12's `closeCase` had to swap its check order because one of its tests combined "wrong actor" with "invalid status" in the same case, and checking ownership first masked the intended 409 behind a 403. This task's `updateCase` keeps the brief's literal order — ownership/role check, then `Submitted`-status check — because none of this task's 4 tests combine those two conditions: the 409 test (`Assigned` status) uses the correct submitter as actor, and the 403 test (wrong actor) uses a case still in `Submitted` status. Traced by hand against all 4 tests before concluding no reordering was needed; confirmed by the actual green run below.
