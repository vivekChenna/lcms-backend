# Task 11 — Escalation

**Date:** 2026-10-04

**What:** Added `PATCH /cases/:id/escalate` end-to-end. `src/modules/cases/cases.workflow.service.ts` exports `setEscalation(dataSource, actor, caseId, isEscalated, reason?)`, which loads the case (`loadCaseOrThrow`, throwing `NotFoundError` for a missing id), authorizes the actor — the assigned legal rep (`caseRow.assignedLegalRepId === actor.id`) or a `legal_manager`/`admin` may change escalation state, anyone else gets `ForbiddenError` — then sets `isEscalated` and `escalationReason` (the reason is cleared to `null` whenever `isEscalated` is set to `false`, and defaults to `null` if omitted while escalating, though `escalateCaseBodySchema`'s own `.refine` already requires a non-empty `reason` whenever `isEscalated: true`), saves, and writes an audit event (`case.escalated` / `case.escalation_cleared`) with before/after snapshots. `cases.routes.ts` wires it as `PATCH /cases/:id/escalate`, gated by `app.authenticate` + `requireRole(['legal_rep', 'legal_manager', 'admin'])`, validated by the existing `caseIdParamsSchema` (params) and `escalateCaseBodySchema` (body, already present in `cases.schemas.ts` since an earlier task), response `caseResponseSchema`. Added `test/integration/modules/cases/escalate.test.ts` (4 cases): the assigned legal_rep escalates with a reason, escalation is cleared (reason nulled out), a legal_rep NOT assigned to the case is rejected with 403, and a legal_manager can escalate a case assigned to someone else.

**Why — `serializeCase(toCaseWithSla(caseRow))`, not a bare `toCaseWithSla(caseRow)`:** Same latent-contract mismatch documented in Tasks 7-10's decision logs: `toCaseWithSla` returns native `Date` instances for six timestamp fields, while `caseResponseSchema` declares them as `z.string()`. Returning the un-serialized row through fastify-type-provider-zod would 500 with `FST_ERR_RESPONSE_SERIALIZATION`. The route calls the already-exported `serializeCase` helper from `cases.routes.ts` (the same helper every prior case-mutation route in this file uses), rather than reintroducing the bug or duplicating the Date-to-ISO-string conversion.

**Note — no query-builder alias concern here:** `setEscalation` only uses `dataSource.getRepository(Case).findOne()` / `.save()` (via the existing `loadCaseOrThrow` helper), not a `createQueryBuilder` with a string alias, so the Task 10 `'case'`-is-a-reserved-keyword issue doesn't apply to this task's code.

Full-suite note: ran all 7 files under `test/integration/modules/cases/` together (30 tests) against the running test container; all passed with no cross-file pollution observed this run.
