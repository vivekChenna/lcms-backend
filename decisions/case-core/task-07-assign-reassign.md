# Task 7 — Assignment (and reassignment)

**Date:** 2026-10-04

**What:** Exported `assertValidLegalRep` from `src/modules/master-data/routing-rules.service.ts` (previously module-private) so it can be reused outside that module. Created `src/modules/cases/cases.workflow.service.ts` with `loadCaseOrThrow`, `assignCase` (validates the state-machine transition to `Assigned` and the target's eligibility via `assertValidLegalRep`, resets `assignmentAcceptedAt` to `null` on every (re)assignment, and logs a `case.assigned` audit event — overridable via an `auditAction` parameter so Task 9's auto-routing path can log `case.auto_assigned` through the same function), `acceptAssignment`, and `rejectAssignment` (the latter two have no caller yet in this task; they exist because later tasks in this sub-project share this workflow module). Created `src/modules/cases/cases.routes.ts` registering `PATCH /cases/:id/assign`, gated to `legal_manager`/`admin` via `requireRole`. Registered `casesRoutes` in `src/app.ts`. Added `test/integration/modules/cases/assign.test.ts` (5 cases: fresh assignment, VC-07 rejection of a non-legal target, 403 for a `legal_rep` caller, PR-23 reassignment resetting acceptance, and 409 on a `Closed` case).

While wiring the route, `toCaseWithSla` (Task 4) returns raw `Date` instances for timestamp fields — confirmed by that task's own unit test, which is not this task's to change — but `caseResponseSchema` (Task 6) declares those same fields as `z.string()`. No route before this one actually serialized a `Case` through `fastify-type-provider-zod`, so the mismatch was latent; it surfaced here as a `500 FST_ERR_RESPONSE_SERIALIZATION` the first time a real request hit the route. Fixed by adding and exporting `serializeCase` in `cases.routes.ts`, converting `assignmentAcceptedAt`/`ackDueAt`/`resolutionDueAt`/`closedAt`/`createdAt`/`updatedAt` to ISO strings before the response leaves the handler.

**Why:** A legal_manager (or admin) needs a way to put a case in a legal_rep's queue, and to redirect it later if the first assignment was wrong — PR-23 explicitly allows overriding an existing assignment, which is why `assignCase` always resets `assignmentAcceptedAt` rather than only doing so when `targetLegalRepId` changes. Reusing `assertTransition` (Task 2) keeps the `Closed`-case rejection and the allowed-transition table in one place rather than re-deriving status rules in the route. Reusing `assertValidLegalRep` (now exported) rather than duplicating its eligibility check keeps VC-07 enforced identically for manual assignment and for routing-rule target validation, so the two call sites can't drift out of sync. The `auditAction` parameter on `assignCase` exists specifically because Task 9's auto-routing flow needs to call the same assignment logic but tag the audit trail differently (`case.auto_assigned` vs `case.assigned`) — adding the parameter now avoids a breaking signature change later. The Date-to-string fix was done at the route boundary (not inside `toCaseWithSla`) and exported as `serializeCase` because the codebase already has this exact convention at the route/service boundary (`audit.routes.ts`, `users.service.ts`), and because `cases.routes.ts` is the shared file Tasks 8-14 will keep extending — giving them one conversion helper to reuse avoids every later route re-deriving the same six-field conversion independently.
