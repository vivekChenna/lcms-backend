# Added a shared resetDatabase() helper to fix cross-file test-isolation leaks

**Date:** 2026-10-04

**What:** Added `test/integration/helpers/reset-db.ts`, exporting `resetDatabase(dataSource)`, which deletes `audit_log`, `information_requests`, `refresh_tokens`, `user_roles`, `routing_rules`, `cases`, `users` in that FK-safe order (each table before anything it references). Every integration test file's `beforeEach`/`reset()` that used to hand-roll its own subset of these DELETEs now calls this one helper instead. Files that additionally clean up tables outside this set (`business_units`/`case_types`/`departments` in `case-entity.test.ts`, `closure_outcomes` in `close.test.ts`, `departments` in `departments.test.ts`) keep those extra lines after the shared call. Two files (`departments.test.ts`, `audit/audit-routes.test.ts`) seeded their fixture users once in `beforeAll` instead of per-test; since the shared helper now deletes `users` on every test, their seeding moved into `beforeEach`, after the reset call. Three files that never did any per-test cleanup at all (`master-data/case-categories.test.ts`, `case-types.test.ts`, `org-structure.test.ts`) were deliberately left untouched — they're designed to tolerate accumulated data (per case-core's own `arrayContaining` fix), and forcing a reset into them risked breaking that design.

**Why:** Running the full suite surfaced intermittent `23503` foreign-key violations (`update or delete on table "users" violates foreign key constraint ... on table "cases"`) in files that had nothing to do with cases — `master-data/departments.test.ts`, `master-data/routing-rules.test.ts`, every `users/*.test.ts` file. Root-caused via systematic bisection (isolating `cases/` alone, then `auth+cases`, then a full fresh-container run with complete output capture) rather than guessed: every integration test file creates its own `DataSource`, and its `afterAll` only calls `ds.undoLastMigration()` — which drops and recreates whichever table belongs to the *last* migration (`information_requests`, as of this sub-project), but never touches `cases`, `users`, or any earlier table. Each file's own `reset()` only ever deleted the handful of tables *it* personally wrote to, with no DELETE at the very end of a file's last test. That meant a row left behind by file N's last test (e.g. a `cases` row referencing a `users` row) silently persisted in the shared Postgres container for every file that ran afterward, for the rest of the suite — until some later file's own `DELETE FROM users` (without first deleting `cases`) hit the FK and failed. This was always a latent risk once `cases` (Phase 2) added a `users` FK, but the FK graph was shallow enough to rarely bite. Adding `information_requests` (`-> cases -> users`, plus its own self-FK) deepened the chain enough that the leak started surfacing routinely across unrelated test files.

The fix was raised by the user directly ("if we are writing raw sql query across application, what's the use of orm" led into a broader look at test raw-SQL usage, which surfaced this suite-wide gap) rather than discovered independently — flagged here since the decision to fix it (rather than leave it as a known pre-existing issue, which was also offered as an option) was the user's call, made explicitly outside the 9-task information-requests plan's scope.

**Verification:** Full suite (`test/unit` + `test/integration`) run twice on genuinely fresh containers (`docker compose down -v && up -d`, not just `down && up` — the test Postgres uses a `tmpfs` data directory, so only a true container recreation guarantees empty state) — 210/210 passing, 50/50 files, both times. `npx tsc --noEmit` clean.

**Tradeoffs:** The helper's table list is a fixed array, not derived from `entities.ts`/the migrations list — adding a new table with a FK into this chain in a future sub-project will need a manual addition to `RESET_TABLES_IN_ORDER`, in the correct position. This is the same manual-upkeep risk every one of the 30 files already had individually; centralizing it in one file makes the next addition a one-line change instead of an N-file hunt, but doesn't make it automatic.
