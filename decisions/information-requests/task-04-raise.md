# Task 4 — Raise an information request

**Date:** 2026-10-04

**What:** Added `src/modules/information-requests/information-requests.service.ts` with `raiseInformationRequest()`, and `src/modules/information-requests/information-requests.routes.ts` registering `POST /cases/:id/information-requests` (role-gated to `legal_rep`). The service loads the case, checks the caller is the assigned legal rep, checks the case is `In Progress` or `Waiting on Input` (409 otherwise), validates the responder is a known active user (400 otherwise), creates the `InformationRequest` row, then calls `markCaseWaitingOnInput()` (a no-op if the case is already Waiting on Input, which is what lets a second concurrent request be raised per WF-08), then logs an `info_request.raised` audit event. The route serializes the response via `serializeInformationRequest()` — the same Date→ISO-string boundary conversion case core's `serializeCase()` does, needed because `fastify-type-provider-zod` doesn't implicitly coerce a `Date` into the `z.string()` fields `informationRequestResponseSchema` declares. Exported so Tasks 5–7's routes in this same file reuse it. Registered the new routes module in `src/app.ts` after `casesRoutes`. Added `test/integration/modules/information-requests/raise.test.ts` covering: happy path (case moves to Waiting on Input, one audit row), a second concurrent request while already Waiting on Input (WF-08), a non-assigned legal_rep (403), and a case still Submitted/not yet accepted (409).

**Why:** This is the first write path in the information-requests module and the first task to wire a new routes module into `app.ts`, so it establishes the request-handling and serialization conventions (service throws typed `AppError`s, route maps input/output via Zod schemas, Date fields are converted at the route boundary) that Tasks 5–7 build on directly. Creating the `InformationRequest` row before transitioning the case (rather than after) means a failure in the case-transition step leaves no orphaned request-less case transition; the row is the source of truth for "is there an open request," which the case-status mutation builds on. Reusing `markCaseWaitingOnInput`'s existing no-op guard rather than adding a duplicate check here is also what makes the second-concurrent-request case (WF-08) work without any extra branching in the service.
