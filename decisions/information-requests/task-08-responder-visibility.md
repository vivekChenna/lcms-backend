# Task 8 — Requester-as-responder visibility extension (case core)

**Date:** 2026-10-04

**What:** Extended `getCaseById()` and `listCases()` in `src/modules/cases/cases.service.ts` (case-core, already shipped) so a `requester` actor also sees a case outside their own department if they are the `responderId` on any information request for it, regardless of that request's status (AC-04). `getCaseById()` falls back to a repository `count()` against the `InformationRequest` entity when the department check fails, rather than immediately 404ing. `listCases()`'s requester-scoping `WHERE` clause became an OR between the existing department match and a raw `EXISTS (SELECT 1 FROM information_requests ir WHERE ir."caseId" = c.id AND ir."responderId" = :actorId)` subquery fragment passed to the query builder (the same idiom every other filter in `listCases` already uses). Added `test/integration/modules/cases/responder-visibility.test.ts` with three cases: an outsider-department requester who is a responder can GET the case by id (200); the same case appears in that requester's GET /cases list; and that requester still gets 403 trying to PATCH /cases/:id/escalate (visibility is not write access).

**Why:** AC-04 requires a requester to see a case they're responding on even when it belongs to a different department. The original implementation used `dataSource.query()` with a raw SQL string for `getCaseById`'s check, reasoning that importing the `InformationRequest` entity would create a circular module dependency (information-requests already imports from case-core via Task 7's reuse of `getCaseById`). That reasoning was only half right: the real cycle risk is between the two *service* files, not the entity. `src/modules/information-requests/entities/information-request.entity.ts` is a pure leaf module — it imports only from `typeorm`, nothing from `cases` — so `cases.service.ts` can safely import just the entity (not the information-requests service) without creating a cycle. This was caught and fixed in a same-day follow-up commit, switching `getCaseById` to `dataSource.getRepository(InformationRequest).count(...)`: type-checked, no hand-written column-name strings, same one-directional module graph. `listCases`'s EXISTS subquery was left as a raw-string fragment, since that's the existing idiom the whole function already uses for every other filter condition (status, priority, category, etc.) — not a bypass of the ORM, just how this query builder's dynamic WHERE clause is built throughout the file.

**Tradeoffs:** `getCaseById`'s extra query only runs for a requester outside their own department (the common case — same-department requester — short-circuits before it). No caching or indexing changes were made to `information_requests` for this read path; if volumes grow, an index on `(caseId, responderId)` would help both this count query and the EXISTS subquery, but that's speculative for now and out of scope for this task.
