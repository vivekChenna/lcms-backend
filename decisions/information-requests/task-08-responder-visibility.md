# Task 8 — Requester-as-responder visibility extension (case core)

**Date:** 2026-10-04

**What:** Extended `getCaseById()` and `listCases()` in `src/modules/cases/cases.service.ts` (case-core, already shipped) so a `requester` actor also sees a case outside their own department if they are the `responderId` on any information request for it, regardless of that request's status (AC-04). `getCaseById()` falls back to a raw `COUNT(*)` query against `information_requests` when the department check fails, rather than immediately 404ing. `listCases()`'s requester-scoping `WHERE` clause became an OR between the existing department match and a raw `EXISTS (SELECT 1 FROM information_requests ir WHERE ir."caseId" = c.id AND ir."responderId" = :actorId)` subquery. Both reference the `information_requests` table by raw SQL string, not a TypeORM entity import. Added `test/integration/modules/cases/responder-visibility.test.ts` with three cases: an outsider-department requester who is a responder can GET the case by id (200); the same case appears in that requester's GET /cases list; and that requester still gets 403 trying to PATCH /cases/:id/escalate (visibility is not write access).

**Why:** AC-04 requires a requester to see a case they're responding on even when it belongs to a different department. Raw SQL (not a TypeORM entity import of `InformationRequest`) is deliberate: case-core shipped before information-requests existed, and information-requests already imports from case-core (it reuses `getCaseById` as its own visibility gate — see Task 7's decision log). An entity import in the other direction would create a circular module dependency. Raw SQL keeps the dependency one-directional: case-core knows the table name but not the module. Using an `EXISTS` subquery (not a `JOIN`) in `listCases` avoids duplicate case rows when a requester has multiple information requests on the same case. The third test exists because visibility and write-authorization are separate concerns in this codebase (escalate has its own role/ownership check) — extending visibility must not accidentally loosen who can mutate the case.

**Tradeoffs:** `getCaseById`'s extra query only runs for a requester outside their own department (the common case — same-department requester — short-circuits before it). No caching or indexing changes were made to `information_requests` for this read path; if volumes grow, an index on `(caseId, responderId)` would help both this COUNT query and the EXISTS subquery, but that's speculative for now and out of scope for this task.
