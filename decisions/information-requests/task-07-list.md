# Task 7 — List information requests for a case

**Date:** 2026-10-04

**What:** Added `listInformationRequestsForCase()` to `src/modules/information-requests/information-requests.service.ts`, and registered `GET /cases/:id/information-requests` in `src/modules/information-requests/information-requests.routes.ts` (authentication required, no role restriction — see "Why" below). The service reuses `getCaseById()` from case-core as a visibility gate (throws `NotFoundError` with status 404 if the case doesn't exist or if it's a requester trying to access a case from a different department), then queries all `InformationRequest` rows for the case ordered newest-first (`createdAt DESC`). The route maps the case ID from URL params, constructs an `Actor` object from the request user, and calls the service function, then serializes each row via `serializeInformationRequest()` to convert `Date` fields to ISO-8601 strings. Added `test/integration/modules/information-requests/list.test.ts` with two test cases: (1) legal_rep lists all requests for a case they can see, verifying the order is newest-first; (2) a requester from a different department (outsider) gets 404 via case visibility.

**Why:** Reusing `getCaseById()`'s existing visibility gate (rather than re-deriving the rule in this service) keeps one single source of truth for "can this actor see this case" — enforced in case-core and reused everywhere: case detail, list, and now information-request list. This makes Task 8's planned extension (allowing a requester who is a responder on the case to see it, without case-core changes) apply automatically to information-request list as well. The route has no explicit role restriction because the visibility gate is already role-aware: `legal_rep` can see any case, while `requester` can only see cases from their own department (extended in Task 8 to also include cases where they're a responder). Ordering newest-first (most recent request first) is a UI-friendly default for exploring a case's communication history. The serialization pattern (Date→ISO-string at the route boundary) matches Task 4's established convention and is required because `fastify-type-provider-zod` doesn't implicitly coerce `Date` into `z.string()` fields. The tests verify both the happy path (correct ordering, all rows returned) and the 404 path (reusing case visibility, not duplicating it here).

**Tradeoffs:** The service function doesn't filter or paginate the results — it returns all matching rows. This is suitable for small result sets (a case typically has a handful of open requests); a later scaling task could add pagination if cases accumulate hundreds of information requests. The function assumes the caller has already been authenticated; the route's `preHandler: [app.authenticate]` ensures this.
