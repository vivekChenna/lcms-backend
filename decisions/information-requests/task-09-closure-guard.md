# Task 9 — Closure guard: no open information requests (VC-12)

**Date:** 2026-10-04

**What:** Added a guard to `closeCase()` in `src/modules/cases/cases.workflow.service.ts` (case-core, already shipped), inserted right after the existing `closureOutcome` validation and before the `before = {...}` snapshot. It counts open information requests for the case via `dataSource.getRepository(InformationRequest).count({ where: { caseId: caseRow.id, status: 'open' } })` and throws `ConflictError` (409) when the count is greater than zero, blocking closure. `ConflictError` was added to the existing `import { NotFoundError, ForbiddenError, ValidationError } from '../../shared/errors'` line. Added `test/integration/modules/cases/close.test.ts`'s new test "rejects closing a case with an open information request (VC-12)", seeding an open information request on an In-Progress case and asserting 409 on `PATCH /cases/:id/close`. Also added the `seedInformationRequest` import and a `DELETE FROM information_requests` line to that file's `reset()` helper, ordered before the `cases` delete since `information_requests.caseId` has a `RESTRICT` foreign key to `cases`.

**Why:** VC-12 was deliberately deferred from case-core because the `information_requests` table didn't exist yet when `closeCase` shipped (see the comment removed from above `closeCase` in this task). Now that sub-project 2 has shipped the table, the guard closes that gap.

The guard references `InformationRequest` via a direct entity import (`import { InformationRequest } from '../information-requests/entities/information-request.entity'`), not raw SQL. The entity file is a leaf module — it imports only from `typeorm`, nothing from `cases` — so importing it from `cases.workflow.service.ts` carries no circular-import risk. The real cycle risk in this codebase is between the two *service* files (`information-requests.service.ts` imports from `cases.service.ts` to reuse its visibility gate), not between an entity and a service. Task 8's raw-SQL choice for the responder-visibility extension in `cases.service.ts` conflated these two risks; this task's guard uses the safer, more idiomatic `.count()` call instead since no such conflation applies here — the dependency is case-core depending on an information-requests leaf type, which is fine one-directionally. (Task 8's existing raw SQL is being revisited separately, outside this task's scope.)

**Tradeoffs:** None beyond what's described above — this is a straightforward count-and-reject check with no caching or indexing changes. If information-request volumes grow, an index on `(caseId, status)` would help this query, but that's speculative and out of scope here.
