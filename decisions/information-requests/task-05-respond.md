# Task 5 — Respond to an information request

**Date:** 2026-10-04

**What:** Added `respondToInformationRequest()` to `src/modules/information-requests/information-requests.service.ts` and registered `POST /information-requests/:id/respond` in `src/modules/information-requests/information-requests.routes.ts`. The service loads the request, checks the caller is the assigned `responderId` (403 otherwise), checks the request is still `open` (409 otherwise), marks it `answered` with the given `responseText`, then counts remaining `open` requests for the same `caseId`. If that count is zero, it calls `markCaseInProgress()` to return the case to `In Progress`; if other open requests remain, the case is left untouched in `Waiting on Input`. Logs an `info_request.answered` audit event, then returns the updated row, serialized via the existing `serializeInformationRequest()` export. Per the Global Constraints (PR-11), the route has no `requireRole(...)` gate — only `app.authenticate` — since a responder can hold any role; the service's own `responderId` check is the real restriction. Added `test/integration/modules/information-requests/respond.test.ts` covering: the only-open-request case returning the case to In Progress, a second open request keeping the case on Waiting on Input, a non-responder getting 403, an already-answered request getting 409, and a responder holding the `legal_rep` role (not `requester`) succeeding.

**Why:** Counting other open requests rather than tracking a count on the case itself keeps `InformationRequest` rows as the single source of truth for "does this case still have outstanding questions," consistent with how Task 4 treated the row as the source of truth for the inverse transition. Doing the count after saving the just-answered row (rather than before) means the row being answered is excluded from the count without needing an explicit `id != requestId` filter — it no longer matches `status: 'open'`. No `requireRole` gate on this route mirrors the Global Constraint that a request's responder is an arbitrary user, not a role-scoped actor, so authorization is answered entirely by the service-layer identity check rather than coarse role gating at the route.
