# Task 6 — Reopen an information request

**Date:** 2026-10-04

**What:** Added `reopenInformationRequest()` to `src/modules/information-requests/information-requests.service.ts` and registered `POST /information-requests/:id/reopen` in `src/modules/information-requests/information-requests.routes.ts`. The service loads the request, checks the caller is the original `raisedById` (403 otherwise), checks the request is still `answered` (409 otherwise — `open` and `superseded` are both rejected), marks the old row `superseded`, then creates a brand-new row with `status: 'open'`, `requirementDescription` set to the caller's `comment`, `responseText: null`, `dueDate: null`, and `reopenedFromId` pointing at the superseded row. It then unconditionally calls `markCaseWaitingOnInput()` — unlike `respondToInformationRequest()` (Task 5), there is no counting of other open requests first; reopening always forces the case back to `Waiting on Input`, even if the case had already returned to `In Progress` because every other request on it was answered. Logs an `info_request.reopened` audit event, then returns the newly-created row (not the superseded one), serialized via `serializeInformationRequest()`. The route gates on `requireRole(['legal_rep'])` since in practice `raisedById` is always a legal_rep; the service's own `raisedById` check is the real authorization. Added `test/integration/modules/information-requests/reopen.test.ts` covering: the raiser reopening an answered request (new row created, old row superseded, case → Waiting on Input), the case being forced back to Waiting on Input even when it's already In Progress with no other open requests, a non-raiser getting 403, and a still-`open` request getting 409.

**Why:** The unconditional transition is the one piece of real judgment in this task: `respondToInformationRequest` only resumes the case when the count of remaining open requests hits zero, because answering doesn't necessarily mean the case is unblocked (other requests may still be open). Reopening is the opposite situation — the legal rep is explicitly saying "this answer wasn't good enough," so the case must go back to Waiting on Input regardless of what state it's currently in; checking for other open requests here would be backwards (there's exactly one new open request as a direct result of this call, so the count would always force the transition anyway, making an explicit check both redundant and misleading as documentation of intent). Returning the new row rather than the superseded one matches the produced-interface contract and lets the caller immediately see the new row's id, `reopenedFromId`, and the caller's `comment` as `requirementDescription`. Superseding rather than deleting the old row preserves full history on the case (raise → answer → reopen) for audit purposes, consistent with how `status` is used as the historical record for every other transition in this entity.
