# Task 12 — Demo seed data (`pnpm seed:demo`)

**Date:** 2026-10-10

**What:** Added `src/db/seed-demo.ts` (`seedDemo(dataSource)` plus a `main()` behind `pnpm seed:demo`). It creates one user per role (`vivekadmin@`, `viveklegalmanager@`, `viveklegalrep@`, `viveklegalrep2@`, `vivek@` as requester, `vivekviewer@` — all `@gmail.com`, password `Password123!`), fills in only the missing master data (a Commercial category, a case type under Internal and Commercial, Finance and Operations departments, a Head Office business unit under the migration-seeded AGC entity, Resolved and Withdrawn closure outcomes), and creates eight cases through the real services (`submitCase`, `assignCase`, `acceptAssignment`, `raiseInformationRequest`, `setEscalation`, `closeCase`, `createComment`): Submitted, Assigned, In Progress (with an internal and a public comment), Waiting on Input, escalated, Closed, confidential Submitted, and one whose `resolutionDueAt` is pushed into the past so its SLA is breached.

**Why:** The frontend and the e2e tests need a populated dev database. Going through the real services gives correct reference numbers, SLA dates, notifications and audit rows, which raw inserts would not. The seed is idempotent: users are found by email, master data by name, and cases by their fixed `[Demo] ...` title, so a second run creates nothing and returns the same ids. A case that already exists is not re-advanced, so a run that crashed halfway leaves that one case in its partial state. It throws when `NODE_ENV=production`. The breached-SLA case is made by a direct `resolutionDueAt` update on the repository that deliberately bypasses the services, because no service can move a due date into the past. `main()` runs on a DataSource clone with logging off so the command prints only the credentials table.
